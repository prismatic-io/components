This trigger retrieves existing and ongoing projects from the [Microsoft Project Web App ProjectData OData service](https://learn.microsoft.com/en-us/previous-versions/office/project-odata/jj163015(v=office.15)). Load history once, check for changes on a schedule, or both.

#### How It Works

On each scheduled recurrence, the trigger fetches projects from the `/Projects` endpoint, applying a server-side OData `$filter` against `CreatedDate` and/or `LastPublishedDate` so only records changed since the previous poll are returned. Records are categorized as **created** or **updated** based on their timestamps relative to the last poll time.

If both **Show New Records** and **Show Updated Records** are disabled, the trigger short-circuits without making an API request and emits an empty result.

**Initial sync**

An initial sync seeds a complete starting state. Because the goal is a full snapshot from the look-back date, all matching projects are returned regardless of the **Show New Records** and **Show Updated Records** toggles.

When **Look-back Date** is set, the first recurrence begins fetching all projects modified on or after that date via the OData `$filter`. The window has no fixed upper bound, so a project modified mid-drain is swept into the sync. Once all matching projects have been emitted, the trigger stores the current time as its position and the next recurrence resumes from there as a normal incremental poll. Without batching enabled, the full window is fetched in a single recurrence; with batching enabled, the resolver drains the window over batched executions within the same recurrence.

When **Look-back Date** is not set, the first recurrence records the current time as the cursor and emits nothing, so a flow does not receive a backlog of historical projects on deploy.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Microsoft Project.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps receive `results.body.data.created` and `results.body.data.updated` arrays. With batching on, those fields do not exist — each execution receives a single `{ changeType, record }` object. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.

#### Notes

- Only the top-level `/Projects` collection is polled. Tasks, Assignments, and other child resources require a parent project GUID and are not exposed as pollable resources.
- The `$filter` clause is applied server-side, so only records modified since the last poll are returned — this minimizes data transfer on each execution.
- Project Web App OData v3 returns responses in `{ d: { results: [...] } }` envelope format in verbose mode; the trigger also handles `{ value: [...] }` and `{ results: [...] }` shapes for compatibility with newer endpoints.
- Refer to the [Projects entity set reference](https://learn.microsoft.com/en-us/previous-versions/office/project-odata/jj163621(v=office.15)) for the available fields on the `Projects` entity.
