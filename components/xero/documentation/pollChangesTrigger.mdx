This trigger retrieves existing and ongoing records for a selected Xero resource type. Load history once, check for changes on a schedule, or both.

#### How It Works

On each scheduled recurrence, the trigger fetches records from the selected Xero endpoint using a server-side `If-Modified-Since` filter. Records are classified as **created** when their ID was not seen in a previous poll, and otherwise as **updated**. The trigger persists the set of known IDs between recurrences.

On the first recurrence without a Look-back Date, the trigger records the current set of IDs and emits nothing. Subsequent recurrences compare the fetched IDs against the stored set and report additions and modifications.

**Initial sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it: it ignores **Show New Records** and **Show Updated Records**. It begins on the first recurrence when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set. The date is passed as the `If-Modified-Since` header, so the API returns only records modified on or after that date. All returned records are classified as "created" (the known-ID set is empty), so each is seeded once. Left empty, there is no sync and the trigger starts from its first recurrence.

The sync completes in a single recurrence regardless of whether batching is enabled. Without batching, all changes are returned in one payload. With batching, the resolver dispatches each record (or batch of records) as a separate execution within the same recurrence. The request has no upper bound. The trigger stores the returned IDs and the time that recurrence started as its position, and the next recurrence sends that time as `If-Modified-Since`, so a record modified during the sync is returned again as updated and nothing is lost. No field in the payload marks the handoff.

**Resource Type** still applies: it selects the endpoint the sync reads from. **Show New Records** and **Show Updated Records** apply again from the next recurrence onward.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Xero.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps read `results.body.data.created` and `results.body.data.updated`. With batching on, those fields do not exist — each execution receives a single `{ changeType, record }` object. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.

#### Returned Data

The trigger returns an object with two arrays — `created` for new records and `updated` for modified records. Fields shown are representative. The full response object includes additional properties.
