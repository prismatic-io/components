This trigger polls the [Sage 200 Professional/Extra Online API](https://developer.sage.com/200-uk) for new and updated records of the selected resource type on a configured schedule.

#### How It Works

1. The trigger runs on the configured schedule (e.g., every 5 minutes)
2. On each execution, records of the selected resource type are fetched from Sage 200 using the corresponding list endpoint with a server-side OData filter (`$filter=date_time_updated gt {lastPolledAt}`) so only records changed since the previous poll are returned
3. Returned records are categorized client-side as **created** or **updated** by comparing each record's `date_time_created` and `date_time_updated` against the timestamp of the last successful poll
4. A record is classified as **created** when `date_time_created` is newer than the last poll time; otherwise, when `date_time_updated` is newer than the last poll time, the record is classified as **updated** (created beats updated)
5. The trigger updates its internal state with the current timestamp after each poll so subsequent executions only surface records changed since the previous run
6. When no records match on a given run, the trigger reports `polledNoChanges` so downstream flows are not invoked unnecessarily
7. On the first recurrence without a **Look-back Date**, the trigger only records the time of the run, so only changes that occur after the trigger is enabled are surfaced. With a **Look-back Date** set, the first recurrence runs the initial sync described below

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it: **Show New Records** and **Show Updated Records** are ignored while it runs, and are the only inputs it ignores. It begins on the first recurrence, when the trigger has no stored time and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every record modified on or after the start of that day (UTC) exactly once.

The window has no fixed upper bound, so a record modified mid-drain is swept into the sync rather than deferred to the schedule. The sync reads the whole window in a single request within one recurrence, whether or not batching is on. The trigger then stores the time the recurrence started, and the first incremental recurrence resumes from exactly there; nothing in the payload marks the handoff. The toggles apply again from that recurrence on.

**Resource Type**, **Site** and **Company** still apply during the sync. The trigger has no page-size or field-selection input.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Sage 200.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

Batching splits one recurrence's records into separate executions; it does not change how many are fetched.

With batching off a downstream step reads `body.data.created` and `body.data.updated`. With batching on those fields do not exist: each execution receives one `{ "changeType": ..., "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

#### Notes

- The trigger sends `lastPolledAt` directly to the Sage 200 OData `$filter` query as an ISO 8601 string (e.g. `2026-04-27T10:00:00Z`). The API parses the ISO string directly. No datetime literal wrapping is required
- Outside the initial sync, when both *Show New Records* and *Show Updated Records* are disabled, the trigger short-circuits without calling the API and reports `polledNoChanges`
- A record qualifying as both new and updated is reported as **created** (created beats updated) so downstream flows do not process the same record twice on the run it first appears
- Refer to the [Sage 200 Professional/Extra Online API Reference](https://developer.sage.com/200-uk) for rate limit details and the full set of fields available on each resource type
