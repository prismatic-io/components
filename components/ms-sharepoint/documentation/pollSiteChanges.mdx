Checks for new and updated items across all drives in a SharePoint site on a configured schedule.

This trigger monitors all drives within a site for file and folder changes using Microsoft Graph's delta tracking. For monitoring a specific drive or folder, use the **New and Updated Drive Items** or **New and Updated Folder Items** triggers instead.

#### How It Works

1. Run on the configured schedule (e.g., every 5 minutes)
2. Retrieve all drives in the specified SharePoint site
3. For each drive, query the Microsoft Graph delta endpoint to detect changes
4. Categorize items as "added", "updated", or "deleted" based on their properties and timestamps
5. Maintain delta tracking state automatically for each drive to efficiently track changes between polls

The trigger uses Microsoft Graph's [delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview) functionality to track changes efficiently without scanning all items on each poll.

On the first recurrence there is no stored delta link, so Microsoft Graph returns the full current state and the trigger emits every existing item once. There is no history to seed, so the trigger has no look-back input. Later recurrences emit only changes since the previous one.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own
execution, or grouped by the configured batch size. Batch size and batch concurrency can both be
overridden per instance. Raising concurrency increases the request volume sent to Microsoft Graph.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable
Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**.
**Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching on, the trigger reads one page per round from one drive at a time, moving through the site's drives in turn and passing over drives with no changes in the same round, and is called again until every drive's walk is complete, so a large first recurrence is delivered over several rounds instead of in one payload. Each drive keeps its own delta link. The new delta link is stored only once the last page has been read, and the position reached is saved after every round, so a recurrence that stops partway resumes where the walk stopped. Microsoft Graph can return the same item on more than one page, so with batching on an item can occasionally arrive in two executions, the later one carrying its newer state. With batching on, if Microsoft Graph can no longer serve a stored delta link or page (HTTP 410 Gone), the trigger restarts the walk from the beginning, which emits every existing item again, as on the first recurrence. With batching off, each recurrence still reads every page in one execution.

With batching off, a downstream step reads `body.data`, keyed by drive display name, where each value holds `deleted`, `added` and `updated` arrays. With batching on those fields do not exist: each execution receives one `{ "changeType": "deleted" | "added" | "updated", "record": <drive item> }` item, or an array of them when the batch size is greater than 1. A batched item does not carry the drive display name; the record's `parentReference.driveId` identifies the drive. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow rather than to the component or to other flows using the same trigger.

#### Returned Data

With batching off, the trigger returns changes grouped by drive name, with separate arrays for added, updated, and deleted items. Fields shown are representative. The full response object includes additional properties.
