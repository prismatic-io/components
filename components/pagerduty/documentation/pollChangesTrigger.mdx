This trigger retrieves existing and ongoing incidents from PagerDuty. Load history once, check for changes on a schedule, or both.

#### How It Works

On each scheduled recurrence, the trigger calls the PagerDuty REST API to retrieve incidents created since the previous poll time. Incidents are placed in the `created` array; the `updated` array is always empty because PagerDuty incident listing is filtered by creation time only. When no new incidents are returned, the trigger signals no changes so the flow does not execute downstream steps.

**Initial sync**

An initial sync seeds a complete starting state rather than a change feed. It begins on the first recurrence when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every incident created on or after that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound, so an incident created mid-drain is swept into the sync. Once all matching incidents have been emitted, the trigger stores the current time as its position and the first incremental recurrence resumes from exactly there. Without batching the full window is fetched in a single recurrence; with batching the resolver drains the window over batched executions within the same recurrence.

**Show New Incidents** is the only toggle and it is not suppressed during the sync.

**Batching**

Batching is enabled per flow on this trigger: each incident is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to PagerDuty.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps read `results.body.data.created` and `results.body.data.updated`. With batching on, those fields do not exist — each execution receives a single `{ changeType, record }` object. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.

#### Returned Data

The trigger returns an object with two arrays — `created` for new incidents and `updated` (always empty). Fields shown are representative. The full response object includes additional properties.
