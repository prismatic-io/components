The **New Event Steps** trigger checks Workday on a schedule for business process event steps (see the [Workday REST Services](https://community.workday.com/sites/default/files/file-hosting/restapi/index.html) Business Process API) created since the previous recurrence. **It emits new event steps only**: event steps carry a creation date but no modification date, so changes to existing steps (completion, reassignment, a new due date) are not reported.

#### How It Works

1. The trigger runs on the configured schedule and records the time each recurrence starts.
2. It requests `GET /businessProcess/v1/eventSteps` with `createdOnOrAfter` set to the day before the previous recurrence's UTC date. The filter is date-only and Workday dates follow the tenant's time zone, so the extra day covers any offset from UTC. **Business Process** and **Step Type** narrow the request when set.
3. It reads every page by limit and offset until the reported total is reached. A window needing more than 1,000 pages fails with an error rather than delivering part of it.
4. Steps whose ID was already returned by the previous recurrence are skipped. The trigger stores the recurrence start time and the IDs of steps created on or after the next window's start date, so the stored set holds about two days of steps, and returns the remaining steps. Up to 10,000 IDs are kept. When more than 10,000 steps fall in that range, the recurrence logs a warning with the count and the limit and keeps the IDs of the most recently created steps; a step whose ID was dropped is delivered again if the next window returns it.

Results are secured by Workday: only steps from events the integration user can view are returned.

**Initial Sync**

An initial sync seeds a complete starting state. **Business Process** and **Step Type** still narrow the steps it reports, so no input is ignored while it runs. It begins on the first recurrence, when the trigger has no stored state and a **Look-back Date** (`YYYY-MM-DD`) is set: `createdOnOrAfter` is that date and every returned step is delivered exactly once. Left empty, there is no sync: the first recurrence reads steps created since the previous day, records their IDs, and delivers nothing.

The window has no fixed upper bound, so a step created mid-sync is swept into the sync. The sync reads the whole window in a single recurrence, whether or not batching is on. The trigger then stores the time that recurrence started, and the first incremental recurrence resumes from the day before it, skipping steps already delivered; nothing in the payload marks the handoff.

**Business Process** and **Step Type** still apply during the sync.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Workday.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.created`. With batching on that field does not exist: each execution receives one `{ "changeType": "created", "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

With batching off, the trigger returns an object under `body.data` with one array, `created`, holding event step records.
