This trigger polls the [Gorgias REST API](https://developers.gorgias.com/reference/introduction) for new and updated records of the selected resource type on a configured schedule.

#### How It Works

1. The trigger runs on the configured schedule (e.g., every 5 minutes)
2. On each execution, all records of the selected resource type are fetched from Gorgias using the corresponding list endpoint with full pagination
3. Because Gorgias list endpoints do not support server-side date filtering, records are categorized client-side as **created** or **updated** by comparing each record's `created_datetime` and `updated_datetime` against the timestamp of the last successful poll
4. Records whose `created_datetime` is newer than the last poll time are classified as created; records whose `updated_datetime` is newer (but were created before the last poll) are classified as updated
5. The trigger updates its internal state with the current timestamp after each poll so subsequent executions only surface records changed since the previous run
6. When no records match on a given run, the trigger reports `polledNoChanges` so downstream flows are not invoked unnecessarily

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it: **Show New Records** and **Show Updated Records** are ignored while it runs. It begins on the first recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every record created or modified since 00:00:00 UTC on that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound, because every recurrence fetches the full record list and filters it client-side. The sync finishes in one recurrence whether batching is on or off, and a record modified during the fetch can be delivered again as an update on the next recurrence. The first incremental recurrence resumes from the stored position, so nothing is lost, and nothing in the payload marks the handoff. The toggles apply from the recurrence after the sync ends.

**Resource Type** still applies throughout. The trigger has no page-size or field-selection input, so nothing else is suppressed.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Gorgias.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, a downstream step reads `body.data.created` and `body.data.updated`. With batching on, those fields do not exist: each execution receives one `{ "changeType": "created" | "updated", "record": <record> }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow rather than to the component or to other flows using the same trigger.

The trigger still fetches the full record list on every recurrence; batching splits the changed records across executions and does not reduce what is fetched.

#### Supported Resource Types

The trigger currently supports the following Gorgias resources:

- **Tickets**: polls the `/api/tickets` endpoint
- **Customers**: polls the `/api/customers` endpoint

#### Returned Data

With batching off, the trigger returns an object containing two arrays: `created` for newly created records and `updated` for modified records. Each array contains full Gorgias resource objects matching the selected resource type. Fields shown are representative. The full response object includes additional properties.

#### Notes

- Gorgias list endpoints do not support server-side filtering by date, so the trigger fetches all records on each run and filters client-side. For workspaces with very large record volumes, consider tuning the polling schedule to balance freshness against API rate limits
- On the very first execution with no **Look-back Date**, the trigger has no prior poll timestamp and uses the current time as its baseline, so no historical records are emitted on the initial run. Only changes that occur after the trigger is enabled will be surfaced
- Refer to the [Gorgias REST API documentation](https://developers.gorgias.com/reference/introduction) for rate limit details and the full set of fields available on each resource type
