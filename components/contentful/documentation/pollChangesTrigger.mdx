Retrieves existing and ongoing entries for a specified [Contentful](https://www.contentful.com/) environment. Load history once, check for changes on a schedule, or both. Each recurrence queries the [Content Management API](https://www.contentful.com/developers/docs/references/content-management-api/overview/) for entries whose `sys.updatedAt` is at or after the trigger's stored position, then sorts them into newly created and modified entries. Use this trigger to drive a flow whenever content changes in Contentful without configuring a webhook in the vendor dashboard.

Both new and updated entries are reported by default. Each category can be disabled independently through the trigger inputs, so a flow can react to only new entries, only modified entries, or both.

#### How It Works

1. The trigger runs on the configured schedule (for example, every five minutes).
2. It queries the selected Contentful space and environment for entries whose `sys.updatedAt` is at or after the stored position, oldest first, ordered by `sys.updatedAt` and then `sys.id`. An optional **Content Type ID** filter narrows the query to a single content type.
3. Each returned entry is sorted by comparing its `sys.createdAt` to the stored position:
   - Entries created after the previous poll are reported as **created**.
   - Entries that already existed but were modified since the previous poll are reported as **updated**.
4. The **Show New Entries** and **Show Updated Entries** inputs control which categories are included. A category that is turned off is omitted from the results.
5. Entries are fetched in pages of 100. Each page is anchored on the last `sys.updatedAt` seen rather than on a page offset, so an entry edited mid-recurrence is fetched again rather than skipped. An entry fetched twice is reported once, de-duplicated by entry ID.
6. A recurrence stops after 50 pages (5,000 entries), or 5 pages (500 entries) when batching is enabled. A recurrence that finishes stores its start time as the trigger's position. A recurrence that stops at the page cap stores the newest `sys.updatedAt` it delivered, and the next recurrence resumes from there. If a full page cap of entries shares one `sys.updatedAt`, the position cannot advance, the next recurrence fetches the same entries again, and a warning is logged.
7. When no entries match, the trigger reports that the recurrence produced no changes and the flow does not continue.

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so the inputs that narrow which changes are reported would leave gaps in it: **Show New Entries** and **Show Updated Entries** are ignored while it runs. It begins on the first recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`, not a future date) is set, and seeds each entry modified on or after that date once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound, so an entry modified mid-drain is swept into the sync. A sync that stops at the page cap continues from the newest entry it delivered on the next recurrence, and keeps ignoring the toggles until it finishes. The page cap applies with batching on or off, so a large history spans several recurrences either way, and more of them with batching on. Nothing in the payload marks the handoff to change tracking.

**Content Type ID** still applies throughout, so a sync seeds only that content type.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own
execution, or grouped by the configured batch size. Batch size and batch concurrency can both be
overridden per instance. Raising concurrency increases the request volume sent to Contentful.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable
Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**.
**Batch Concurrency** is optional; leave it blank for no batch-level limit.

Batching is off by default, and a downstream step reads `body.data.created` and `body.data.updated`. With batching on those fields do not exist: each execution receives one `{ "changeType": "created" | "updated", "record": {...} }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow rather than to the component or to other flows using the same trigger. Both shapes are shown under [Returned Data](#returned-data).

#### Returned Data

Fields shown are representative. The full response object includes additional properties. With batching off, the trigger returns an object under `body.data` with two arrays: `created` holds entries created since the previous recurrence, and `updated` holds entries that existed earlier but were modified. Each entry follows the Contentful entry shape, with a `sys` metadata block and a localized `fields` block.

#### Notes

- Contentful enforces a default rate limit of 7 requests per second on the Content Management API. Avoid very frequent polling schedules to stay within that limit.
- When a recurrence reaches the page cap, a truncation warning is logged and the remaining changes are picked up on the next recurrence, starting from the newest entry delivered. Entries sharing that entry's `sys.updatedAt` may be delivered again.
- An entry that is both created and modified within the same polling window is reported once, in the `created` array.
