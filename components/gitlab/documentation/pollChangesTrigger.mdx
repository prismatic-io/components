This trigger polls the [GitLab REST API](https://docs.gitlab.com/api/rest/) for new and updated issues or merge requests in a project on a scheduled basis. It does not need GitLab to send outbound requests, so it also works for a self-managed instance on a private network that cannot deliver webhooks.

#### How It Works

1. The trigger runs on the configured schedule
2. It fetches the selected **Resource Type** from the project with `updated_after` set to its stored position, ordered by `updated_at` ascending. Each further page starts from the newest `updated_at` already fetched rather than from a page offset, so a record edited during the walk is not skipped. Paging stops once the trigger holds the records it can deliver plus every record sharing the last one's `updated_at`. An unbatched recurrence delivers at most 1,000 records; a batched recurrence delivers at most 500 records and about 4.5 MB of record data
3. Each record is classified as **created** when its `created_at` is later than the stored position, and otherwise as **updated**. A record landing exactly on the stored position is included only if it was not already delivered on an earlier recurrence
4. Outside an initial sync, **Show New Records** and **Show Updated Records** each gate one of the two result arrays. Turning either off empties that array, and both keys remain present in the payload
5. When records are delivered, the position advances to the newest `updated_at` delivered, a timestamp from GitLab itself, so a GitLab clock that runs behind the scheduler's clock does not cause records to be skipped. A recurrence with no records keeps the position, and a first run without a **Look-back Date** starts from the scheduler's clock

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow
which changes are reported would leave gaps in it: **Show New Records** and **Show Updated
Records** are ignored while it runs, and are the only inputs it ignores. It begins on the first
recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set,
and seeds every record updated on or after that date exactly once. Left empty, there is no sync and
the trigger starts from its first recurrence.

The window has no fixed upper bound, so a record modified mid-drain is swept into the sync rather
than deferred to the schedule. Each recurrence advances the position to the newest record it
actually received, never to the wall clock, and the first incremental recurrence resumes from
exactly there; nothing in the payload marks the handoff. With batching off each recurrence is
capped at 1,000 records; with batching on it is capped at 500 records and about 4.5 MB of record
data. A larger window spans several recurrences before the toggles apply again, and the same caps
apply to a busy project outside an initial sync, with later recurrences delivering the rest.

**Project** and **Resource Type** still apply throughout. The trigger has no page-size or
field-selection input, so nothing else is suppressed.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own
execution, or grouped by the configured batch size. Batch size and batch concurrency can both be
overridden per instance. Raising concurrency increases the request volume sent to GitLab.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable
Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch
Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.created` and `body.data.updated`. With
batching on those fields do not exist: each execution receives one
`{ "changeType": ..., "record": ... }` item, or an array of them when the batch size is greater
than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks
the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to
the flow rather than to the component or to other flows using the same trigger.

The trigger advances its position before dispatching, so a failed execution loses its records
either way: with batching off the whole recurrence's payload, with batching on only that batch.
Records lost this way are not polled again.

#### Returned Data

With batching off, the trigger returns an object with two arrays: `created` for new records and `updated` for modified records. Each record is an issue or merge request as returned by the [Issues API](https://docs.gitlab.com/api/issues/) or [Merge requests API](https://docs.gitlab.com/api/merge_requests/). Fields shown are representative. The full response object includes additional properties.
