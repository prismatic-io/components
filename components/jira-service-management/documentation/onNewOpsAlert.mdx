The **New Ops Alerts** trigger polls the Jira Service Management Ops (Operations) API on a recurring schedule and fires the flow with any alerts created since the previous poll. State is tracked between executions so each alert is only emitted once.

#### How It Works

On each scheduled run, the trigger:

1. Reads the last polled timestamp from polling state. On the first recurrence with no stored position, it uses the **Look-back Date** when one is set, and otherwise the current time
2. Builds an OpsGenie query language filter of the form `createdAt > <epochMs>`, optionally combined with the **Additional Query** input. Refer to the [OpsGenie query language documentation](https://support.atlassian.com/opsgenie/docs/search-queries-for-alerts/) for filter syntax
3. Fetches matching alerts from the [List alerts](https://developer.atlassian.com/cloud/jira/service-desk-ops/rest/api-group-alerts/) endpoint
4. Updates polling state to the current timestamp
5. If no new alerts are found, the flow is not executed (the trigger reports `polledNoChanges: true`)

Filtering happens server-side via the OpsGenie query language. The `createdAt` filter uses epoch milliseconds and must not be converted to an ISO string. The API rejects that format.

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it. This trigger has no such input, so none is ignored. It begins on the first recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every alert created on or after that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound. The position is set to the time the recurrence started, never to the newest alert received, and the first incremental recurrence resumes from exactly there; nothing in the payload marks the handoff. The trigger fetches every matching alert with no per-recurrence cap, so the sync finishes in one recurrence whether batching is on or off.

**Additional Query** still applies throughout, so only alerts matching it are seeded. The trigger has no page-size or field-selection input, so nothing else is suppressed.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Jira Service Management.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data`, an array of alerts. With batching on that field does not exist: each execution receives one `{ "changeType": "created", "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

With batching off, the trigger payload contains an array of new Ops alerts in `body.data`. Each entry is an alert summary from the JSM Ops API. Fields shown are representative. The full response object includes additional properties.

With batching on, each execution receives one alert tagged with how it changed, or an array of such items when the batch size is greater than 1. The `body.data` array is not part of this shape.
