The **New Service Requests** trigger polls the Jira Service Management API on a recurring schedule and fires the flow with any service requests created since the previous poll. State is tracked between executions so each request is only emitted once.

#### How It Works

On each scheduled run, the trigger:

1. Reads the last polled timestamp from polling state. On the first recurrence with no stored position, it uses the **Look-back Date** when one is set, and otherwise the current time
2. Fetches service requests from the [Get customer requests](https://developer.atlassian.com/cloud/jira/service-desk/rest/api-group-request/#api-rest-servicedeskapi-request-get) endpoint, optionally scoped to a specific service desk
3. Filters results to requests with `createdDate.epochMillis` greater than the last polled timestamp
4. Updates polling state to the current timestamp
5. If no new requests are found, the flow is not executed (the trigger reports `polledNoChanges: true`)

Because the `/request` endpoint does not support server-side date filtering, the trigger fetches all accessible requests and filters them client-side. On high-volume service desks, scope the trigger to a single **Service Desk ID** to limit the result set.

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it. This trigger has no such input, so none is ignored. It begins on the first recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every request created on or after that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound. The position is set to the time the recurrence started, never to the newest request received, and the first incremental recurrence resumes from exactly there; nothing in the payload marks the handoff. The trigger fetches every matching request with no per-recurrence cap, so the sync finishes in one recurrence whether batching is on or off.

**Service Desk ID** still applies throughout, so only requests in that service desk are seeded. The trigger has no page-size or field-selection input, so nothing else is suppressed.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Jira Service Management.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data`, an array of service requests. With batching on that field does not exist: each execution receives one `{ "changeType": "created", "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

With batching off, the trigger payload contains an array of new service requests in `body.data`. Each entry is a [customer request](https://developer.atlassian.com/cloud/jira/service-desk/rest/api-group-request/) object. Fields shown are representative. The full response object includes additional properties.
