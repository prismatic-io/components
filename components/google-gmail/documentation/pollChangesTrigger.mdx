This trigger retrieves existing and ongoing email messages for a specified Gmail mailbox. Load history once, check for changes on a schedule, or both.

For real-time notifications instead of scheduled polling, consider using the **Managed Push Notification Events** trigger with Gmail's push notification service.

#### How It Works

On each scheduled recurrence, the trigger calls the Gmail History API with the stored `historyId` to retrieve mailbox changes since the previous poll. On the first recurrence without a **Look-back Date**, it retrieves the current history ID and emits nothing. Subsequent recurrences detect changes from that point forward.

If the stored `historyId` is no longer valid (HTTP 404), the trigger automatically re-syncs by obtaining a new starting history ID.

**Initial sync**

An initial sync seeds a complete starting state from the mailbox's messages rather than from its change history. It begins on the first recurrence when the trigger has no stored history ID and a **Look-back Date** (`YYYY-MM-DD`) is set, searches for messages received after the start of that date (UTC), and returns each match once. No input is ignored while it runs. Left empty, there is no sync and the trigger starts from its first recurrence.

The sync completes in one recurrence whether or not batching is on. Its search has no upper bound, so a message received while it runs is included. Once the search finishes, the trigger stores the history ID of the newest message in the mailbox as its position, and the next recurrence lists history from there; a message received between the end of the search and that read can be missed. No field in the payload marks the handoff. Sync entries carry only `id` (the message ID) and `messages`, without the `messagesAdded` and label fields of a history record.

**User ID**, **Label ID**, and **Get Message Details** still apply. With **Get Message Details** on, each synced message carries its metadata (headers and labels) rather than the parsed body and attachments returned on later recurrences.

**Batching**

Batching is enabled per flow on this trigger: each history record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Gmail.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps read the full `results.body.data` object containing `history` and `historyId`. With batching on, each execution receives a single `{ changeType, record }` item representing one history entry. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.

#### Returned Data

The trigger returns the Gmail history response containing an array of history records and the latest `historyId`. Fields shown are representative. The full response object includes additional properties.
