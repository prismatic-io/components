This trigger polls an FTP server for new and modified files on a scheduled basis.

The trigger checks for:
- **New files**: Files that did not exist in the previous poll
- **Modified files**: Files whose modification timestamp or size has changed since the last poll

#### How It Works

1. The trigger runs on the configured schedule (e.g., every 5 minutes)
2. It lists all files in the specified directory on the FTP server
3. Files are compared against the previous poll's file map (stored in state)
4. Files are categorized as "new" or "modified" based on their presence and attributes
5. The trigger updates its state with the current file map for the next poll

The first recurrence starts from an empty file map, so every file that currently matches **Path**, **Pattern**, and **Include Subdirectories** is reported as new. The trigger has no **Look-back Date** input, because the first recurrence already reports the full current state.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own
execution, or grouped by the configured batch size. Batch size and batch concurrency can both be
overridden per instance. Raising concurrency increases the request volume sent to the FTP server.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable
Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**.
**Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.newFiles` and `body.data.modifiedFiles`. With batching on those fields do not exist: each execution receives one `{ "changeType": "new" | "modified", "file": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Notes

- Files are tracked by path, size, and modification timestamp
- The first poll will return all files as "new"
- Polling frequency should balance freshness with server load
- A common integration pattern involves looping over the returned files to perform actions on each file
