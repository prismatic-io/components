This trigger polls the [Toast Labor API](https://doc.toasttab.com/openapi/) for new and updated time entries on a scheduled basis.

#### How It Works

1. The trigger runs on the configured schedule
2. It fetches time entries from Toast using the `modifiedStartDate` and `modifiedEndDate` filter parameters, passing the last poll time so only entries modified since the previous execution are retrieved
3. Records are categorized as **created** or **updated** by comparing each entry's timestamps to the last poll time. Entries whose `createdDate` is after the last poll time are classified as created, and the remaining entries whose `modifiedDate` is after the last poll time are classified as updated
4. The trigger updates its internal state after each poll

**Initial Sync**

An initial sync seeds a complete starting state. It begins on the first recurrence when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every record modified on or after that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence. A toggle that narrows the change feed would leave gaps in that starting state, so **Show New Time Entries** and **Show Updated Time Entries** are ignored during an initial sync: every seeded record is delivered, classified as created or updated, whichever toggles are off.

The window's upper bound is fixed to the wall clock when the sync begins, so a record modified mid-drain is not picked up by the sync itself. The trigger stores that bound as its position once the window is exhausted, and the first incremental recurrence resumes from exactly there. Nothing in the payload marks the handoff. The trigger fetches the whole window in one request, so the sync finishes in one recurrence whether or not batching is on.

**Restaurant External ID** still applies, so the sync covers only that restaurant. No page-size or field-selection input exists, so nothing else is affected.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Toast.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.created` and `body.data.updated`. With batching on those fields do not exist: each execution receives one `{ "changeType": ..., "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Notes

- The `modifiedStartDate` and `modifiedEndDate` filters are applied server-side, so only time entries modified since the last poll are returned. This minimizes data transfer on each execution
- The Toast Labor API limits the modified date window to a maximum of one month. On the first poll, or when the last poll occurred more than 30 days ago, the start of the window is clamped to roughly 30 days before the current poll time
- A time entry that qualifies as both new and updated is reported as **created** only, since a record cannot be created and updated in the same poll window from the consumer's perspective
- Refer to the [Toast API Reference](https://doc.toasttab.com/openapi/) for rate limit details and the full Time Entry field set
