This trigger retrieves existing and ongoing updated records from Karbon. Load history once, check for changes on a schedule, or both.

#### How It Works

On each scheduled recurrence, the trigger fetches all records of the selected resource type from the Karbon API and filters them client-side for records whose modification timestamp is after the last poll time. All matching records land in the `updated` array — the Karbon API does not expose a creation timestamp, so no created/updated split is performed.

The Karbon REST API does not expose a server-side modification-date filter on list endpoints, so all records are fetched and timestamps are compared in the trigger after retrieval.

**Initial sync**

An initial sync seeds a complete starting state rather than a change feed. It begins on the first recurrence when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every record modified on or after that date exactly once. Left empty, there is no sync and the trigger starts from its first recurrence.

The window has no fixed upper bound, so a record modified mid-drain is swept into the sync. The trigger fetches the full window in a single recurrence regardless of whether batching is enabled. Once all matching records have been emitted, the trigger stores the current time as its position and the first incremental recurrence resumes from exactly there. Without batching, all changes are returned in one payload. With batching, the resolver dispatches each record (or batch of records) as a separate execution within the same recurrence. Nothing in the payload marks the handoff.

**Resource Type** still applies throughout. The trigger has no input that narrows the change feed, so the sync ignores no inputs.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Karbon.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps read `results.body.data.updated`. With batching on, that field does not exist. Each execution receives a single `{ changeType, record }` object. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.

#### Returned Data

The trigger returns an object with an `updated` array containing records modified since the last poll. Fields shown are representative. The full response object includes additional properties.
