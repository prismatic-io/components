This trigger polls [ShipBob](https://www.shipbob.com/) on a configured schedule and emits orders that were created or updated since the previous run. It is a convenient alternative to webhooks when a scheduled pull is preferred over an event push.

For details on the underlying endpoint and its filters, refer to the [ShipBob Get Orders documentation](https://developer.shipbob.com/api/orders/get-orders).

#### How It Works

On each scheduled run, the trigger queries the orders endpoint using ShipBob's `LastUpdateStartDate` filter, scoped to the timestamp of the previous poll. It then splits the results into two groups:

- **Created**: orders whose creation date is after the previous poll.
- **Updated**: orders the update filter returned that were not newly created.

The trigger stores the current run time as the cursor for the next run.

- **First run**: without a **Look-back Date**, the very first execution records the cursor and emits nothing, so an instance does not receive a backlog of historical orders on deploy. With a **Look-back Date** set, the first recurrence runs the initial sync described below.
- **Subsequent runs**: only orders created or updated since the last run are returned.

**Initial Sync**

An initial sync seeds a complete starting state rather than a change feed, so inputs that narrow which changes are reported would leave gaps in it: **Show New Records** and **Show Updated Records** are ignored while it runs, and are the only inputs it ignores. It begins on the first recurrence, when the trigger has no stored cursor and a **Look-back Date** (`YYYY-MM-DD`) is set, and seeds every order modified on or after that date once. An order created on or after the start of that day (UTC) is reported as created; every other order is reported as updated.

The window has no fixed upper bound, so an order modified mid-drain is swept into the sync rather than deferred to the schedule. The sync reads every page of the window within one recurrence, whether or not batching is on. The trigger then stores the time the recurrence started, and the first incremental recurrence resumes from that day, so nothing is lost; nothing in the payload marks the handoff. The toggles apply again from that recurrence on.

**Connection** and **Version** still apply during the sync. The trigger has no page-size or field-selection input.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to ShipBob.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

Batching splits one recurrence's orders into separate executions; it does not change how many are fetched.

With batching off a downstream step reads `body.data.created` and `body.data.updated`. With batching on those fields do not exist: each execution receives one `{ "changeType": ..., "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

With batching off, the trigger returns the matching orders grouped under `created` and `updated`. Fields shown are representative. The full response object includes additional properties.

        "id": 11587429,

  }

With batching on, each execution receives one order tagged with how it changed, or an array of such items when the batch size is greater than 1. The `created` and `updated` arrays are not part of this shape.

#### Notes

- ShipBob's order date filters accept day granularity only (`YYYY-MM-DD`). As a result, orders changed earlier on the same calendar day as the cursor may be re-emitted on a later poll within that day. Downstream flows should be prepared to receive the same order ID more than once and handle repeats safely.
- The "new vs updated" split is computed from each order's creation date, the only timestamp ShipBob exposes on the order body.
