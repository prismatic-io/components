This trigger retrieves existing and new emails for a specified IMAP mailbox. Load history once, check for changes on a schedule, or both.

#### How It Works

On each scheduled recurrence, the trigger connects to the IMAP server and checks the mailbox status. It uses IMAP UIDs to track which messages have already been processed, ensuring each email is returned only once.

On the first recurrence without a **Look-back Date** (or when `uidValidity` changes, indicating the mailbox was rebuilt), the trigger records the current UID state and emits nothing. Subsequent recurrences fetch messages with UIDs above the stored threshold.

When **Fetch Content** is enabled, the full email body and attachment metadata are included in the results. When **Mark as Read** is enabled, fetched messages are flagged as `\Seen` on the server.

**Initial sync**

An initial sync seeds a complete starting state from the mailbox. It begins on the first recurrence when the trigger has no stored UID position and a **Look-back Date** (`YYYY-MM-DD`) is set: an IMAP `SEARCH SINCE` finds the messages whose internal date is on or after that date, and the trigger fetches every message from the lowest matching UID onward, delivering each once. No input is ignored while it runs. A later `uidValidity` change starts a new sync from the same date, so a rebuilt mailbox can deliver messages again. Left empty, there is no sync and the trigger starts from its first recurrence.

The sync completes in one recurrence whether or not batching is on. Its fetch has no fixed upper bound, but the position the trigger stores is the mailbox's next UID as read at the start of that recurrence, so a message that arrives while the sync runs can be delivered again by the next recurrence. Later recurrences fetch from that stored UID onward. No field in the payload marks the handoff.

**Mailbox**, **Fetch Content**, and **Mark as Read** still apply. With **Mark as Read** on, every message the sync delivers is flagged `\Seen`, including older unread messages.

**Batching**

Batching is enabled per flow on this trigger: each email is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the connection volume to the IMAP server.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off, downstream steps read `results.body.data` as an array of email objects. With batching on, each execution receives a single `{ changeType, record }` item representing one email. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, the change is scoped to that flow.
