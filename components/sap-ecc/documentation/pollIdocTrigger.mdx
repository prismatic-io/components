Checks for new IDocs in the SAP EDIDC table on a configured schedule using the DOCNUM field as a high-water-mark cursor. Unlike date-based polling, it relies solely on document number ordering to detect new IDocs since the last poll. Only new IDocs are detected. Updates to existing IDocs are not captured.

#### How It Works

1. The trigger runs on the configured schedule.
2. On the first execution it reads the **Starting DOCNUM** input (or defaults to `0000000000000000`) to seed the cursor.
3. It calls `RFC_READ_TABLE` via SOAP/RFC, querying EDIDC for rows where `DOCNUM > lastDocnum`, applying any optional **Message Type** or **Direction** filters.
4. The highest DOCNUM in the result set becomes the new cursor, which is persisted in polling state.
5. Subsequent executions repeat from step 3 using the stored cursor, ignoring the **Starting DOCNUM** input.

**Initial Sync**

The cursor is the IDoc number rather than a date, so there is no **Look-back Date**. The **Starting DOCNUM** input seeds the first recurrence instead: the default `0000000000000000` reads the full IDoc history from the start, and a known DOCNUM skips every IDoc up to and including it. It is read only when no cursor is stored and is ignored afterwards. **Message Type**, **Direction** and **Row Count** apply from the first recurrence.

Each recurrence reads at most one page of **Row Count** IDocs, so a large history drains over several recurrences, each resuming from the highest DOCNUM received.

**Batching**

Batching is enabled per flow on this trigger: each new IDoc is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to SAP ECC.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.records`. With batching on that field does not exist: each execution receives one `{ "changeType": "created", "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled, or it breaks the moment the switch is flipped. Because batching is enabled per flow, the change is scoped to that flow rather than to the component or to other flows using the same trigger.

With batching on, **Row Count** is capped at 1000 IDocs per recurrence, whatever value is set. With batching off, **Row Count** is the only limit. Batching splits one recurrence's IDocs into separate executions and does not fetch more of them.

#### Returned Data

With batching off, the trigger returns an object containing the matched IDoc records, a count, and the updated cursor value. Fields shown are representative. The full response object includes additional properties.

#### State Management

- The highest DOCNUM from each poll cycle is persisted as the cursor for the next execution.
- On the first execution, the **Starting DOCNUM** input seeds the cursor. After the first successful poll, the persisted cursor is used and **Starting DOCNUM** is ignored.
- If a SOAP call fails, the error is logged and the cursor is preserved so the next poll retries from the same position.
- When no new IDocs are found, the trigger signals `polledNoChanges` so the platform can skip downstream processing.
- The cursor advances before the IDocs are dispatched, so a failed execution loses its IDocs: with batching off the whole recurrence's payload, with batching on only that batch. IDocs lost this way are not read again.
- **Row Count** caps the number of rows read per recurrence. In high-volume environments, consider lowering the poll interval or increasing this value to avoid falling behind. With batching on, the cap described under **Batching** applies.
