This trigger polls the [Ramp API](https://docs.ramp.com/developer-api/v1/overview/getting-started) for new and updated records on a scheduled basis.

#### How It Works

1. The trigger runs on the configured schedule
2. It fetches every record of the selected resource type from Ramp. Timestamp-based resources are filtered client-side by their creation and update timestamps relative to the last poll time; ID-based resources are compared against the known ID set
3. Records are categorized as **created** or **updated** based on their timestamps relative to the last poll time, or as **created** only for ID-based resources where update detection is not supported
4. The trigger updates its internal state after each poll

**Initial Sync**

An initial sync seeds a starting state from history. Inputs that narrow which changes are reported would leave gaps in that state, and this trigger does not suppress them: **Show New Records** and **Show Updated Records** still gate the `created` and `updated` arrays. For timestamp-based resources the sync begins on the first recurrence, when the trigger has no stored position and a **Look-back Date** (`YYYY-MM-DD`) is set, and delivers each record created or updated after that date. **Transactions** and **Bills** carry no update timestamp, so only records created after that date are included. ID-based resources (**Departments**, **Locations**, **Business Entities**) ignore **Look-back Date**: their first recurrence delivers every current record as **created**, with or without it.

The window has no fixed upper bound and no per-recurrence cap: the trigger lists every record of the resource and filters client-side, so the sync completes in one recurrence whether batching is on or off. The position is then set to the wall-clock time at which that recurrence started, not to the newest record received, and the first incremental recurrence resumes from there. A record updated after that time but before the listing finished is delivered again on the next recurrence. Nothing in the payload marks the handoff.

**Resource Type** still applies. The trigger has no page-size or field-selection input.

**Batching**

Batching is enabled per flow on this trigger: each changed record is dispatched as its own execution, or grouped by the configured batch size. Batch size and batch concurrency can both be overridden per instance. Raising concurrency increases the request volume sent to Ramp.

To turn it on, select the flow's trigger, open the **Flow control** tab, and switch on **Enable Batching**. Under **Batch Size**, keep **Trigger default** or choose **Custom batch size**. **Batch Concurrency** is optional; leave it blank for no batch-level limit.

With batching off a downstream step reads `body.data.created` and `body.data.updated`. With batching on those fields do not exist: each execution receives one `{ "changeType": ..., "record": ... }` item, or an array of them when the batch size is greater than 1. Any step reading the older shape must be updated before batching is enabled. Because batching is enabled per flow, that change is scoped to the flow rather than to the component or to other flows using the same trigger.

#### Returned Data

The trigger returns an object with two arrays: `created` for new records and `updated` for modified records.

#### Notes

- **Departments**, **Locations**, and **Business Entities** use ID-based change detection: the **Show Updated Records** toggle has no effect for these resource types, as update detection is not supported
- Reimbursements, Vendors, General Ledger Accounts, and Custom Accounting Fields support both new and updated record detection. Transactions and Bills expose only a creation timestamp, so they support new record detection only
- Refer to the [Ramp API documentation](https://docs.ramp.com/developer-api/v1/overview/getting-started) for rate limit details and available fields per resource type
